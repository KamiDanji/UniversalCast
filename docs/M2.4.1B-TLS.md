# M2.4.1b - Android TLS WebSocket transport

Status: Node fingerprint-pinning and pairing/authentication clients added; Android device interoperability validation pending.

## Scope

The Android receiver now derives a TLS 1.2 server context from the existing P-256 Android Keystore identity. Java-WebSocket serves the existing UCP dispatcher over WSS on port 8766. The existing development `ws://` endpoint remains on port 8765 for the M2.2/M2.3 simulator workflow.

Both endpoints and DNS-SD discovery are restricted to debug builds. Release builds still expose no remote-control listener or receiver discovery. The debug WSS endpoint supports pairing and per-connection sender authentication, while remaining debug-only and pending device interoperability checks. The TLS certificate identifies the receiver; paired sender keys authenticate and authorize control. Use only on a controlled development LAN.

## Identity and transport behavior

- The Android Keystore private key is passed to the platform `KeyManagerFactory`; key bytes are never exported.
- The server is pinned to TLS 1.2 for Android API 23 compatibility.
- Before starting WSS, the app checks certificate validity, EC key type, self-signature, and digital-signature usage when the certificate declares key usage.
- The app logs only the public certificate SHA-256 fingerprint for manual development pinning.
- DNS-SD continues to advertise the existing plaintext development endpoint (`tls=0`). It does not claim WSS availability or publish a fingerprint until sender discovery and pairing are updated.
- TLS setup failure leaves the debug plaintext development endpoint available and reports WSS as unavailable. This fallback is debug-only and must not be carried into production.

## Validation

Build the debug APK with `apps/android-receiver/gradlew.bat :app:assembleDebug`. Then on an Android TV or emulator, inspect the `UniversalCastIdentity` log for the fingerprint and confirm that a WSS client pinned to that fingerprint can complete the TLS handshake on port 8766. A client with a different fingerprint must reject the connection before sending UCP data. The Node client is available but has not been run against a device. M2.4.1b is not complete until cross-platform device verification passes.

Do not treat a successful APK build as proof that Android Keystore's generated certificate works for TLS on every supported Android TV device.

## Cross-platform fingerprint client

The receiver simulator includes a Node client that pins the exact SHA-256 fingerprint before the WebSocket HTTP upgrade, verifies TLS 1.2, sends connection.hello, and validates the fresh connection.auth.challenge event. A second client exercises QR challenge pairing, TV approval, reconnect authentication, and a secure ping. It generates an ephemeral sender key for the run; revoke that test sender from the TV after testing.

With the receiver running in a debug build, run from the repository root:

    pnpm --filter @universalcast/receiver-simulator test:android-wss -- --url "wss://<receiver-ip>:8766/ucp" --fingerprint "<fingerprint-from-Android-log>"

To check rejection of an incorrect pin, run the same command with --expect-pin-failure and a deliberately incorrect 64-digit fingerprint. The client should report that the pin was rejected before the WebSocket request was sent. For a full pair/approve/reconnect/authentication run, read the receiver ID and challenge from the QR dialog and run:

    pnpm --filter @universalcast/receiver-simulator test:android-pairing -- --url "wss://<receiver-ip>:8766/ucp" --fingerprint "<fingerprint>" --receiver-id "<receiver-id>" --challenge "<challenge>" --expires-at "<expiry-timestamp>" --expect-role controller

Compare the six-digit SAS shown by the Node client with the TV approval prompt before approving. Select the same role requested with --expect-role.

These clients have not yet been run against a device. M2.4.1b and the M2.4 pairing/authentication stages remain pending until the valid and invalid pin cases and full pairing flow pass on an Android TV or emulator.

## Next

Pairing and authentication are now implemented on the debug WSS endpoint. The release build still disables remote control until the device interoperability matrix passes and production discovery is migrated to authenticated WSS.
