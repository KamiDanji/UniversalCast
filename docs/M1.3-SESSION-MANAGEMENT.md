# M1.3 — Session management (development simulator)

## Scope

The receiver simulator now supports the initial session lifecycle actions:

- `session.create` — creates a receiver-generated UUID session and returns an idle authoritative snapshot.
- `session.join` — attaches a connection as controller when the session has no active controller.
- `session.snapshot` — returns the authoritative snapshot to the attached controller.
- `session.leave` — releases the controller lease while preserving the receiver-owned session.

Each session snapshot contains `revision`, `status`, `mediaId`, `positionMs`, `durationMs`, `bufferedMs`, `playbackRate`, and `updatedAt`. A newly created session starts at revision `0`, status `idle`, and playback rate `1`.

## Disconnect behavior

A WebSocket disconnect releases that connection's controller lease. It does not delete the session. Another connection can join by session ID in this development simulator. This is intentionally not a production authorization model: pairing and cryptographic authorization are not implemented yet, so session IDs must not be treated as secrets or access credentials.

## Current limitations

- Sessions are held in memory and are lost when the receiver process exits.
- No media engine is connected; snapshots remain idle in this milestone.
- No persistence, expiration policy, multi-observer roles, or cryptographic pairing is implemented.
- The simulator allows a sender who knows a session ID to join after the previous controller leaves/disconnects. Production must require paired-device authorization and explicit roles.

## Run tests

```powershell
pnpm --filter @universalcast/receiver-simulator test
pnpm --filter @universalcast/receiver-simulator typecheck
```

The tests cover creation, snapshot retrieval, controller exclusivity, leave/rejoin, and unknown sessions in addition to the M1.2 protocol tests.
