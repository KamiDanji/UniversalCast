# M2.2 — Android UCP WebSocket Control Endpoint

Status: implementation patch; awaiting user build and live interoperability verification.

## Scope

The Android TV app starts a development UCP 1.0 WebSocket endpoint at `ws://0.0.0.0:8765/ucp` while the Activity is alive. Protocol/session/player operations are serialized on the Android main looper so Media3 is only accessed from its application looper.

Implemented actions:

- `connection.hello` / `connection.welcome` with UCP 1.0 negotiation and conservative receiver capabilities.
- `connection.ping` / `connection.pong`.
- `session.create`, `session.join`, `session.snapshot`, `state.snapshot`, `session.leave`.
- `media.load` using the first compatible HTTP(S) source in the descriptor.
- `media.unload` and `playback.stop`.
- `playback.play`, `playback.pause`, `playback.seek`.
- Receiver-originated `state.changed` events carrying the Media3 playback snapshot.

The Android receiver has one Media3 player and therefore allows one active receiver session at a time. A disconnected controller is detached but the session and playback are preserved in memory so another connection can join. Process death clears the in-memory session.

## Development-only security boundary

This milestone intentionally does not implement the UCP specification's production transport security requirements. The endpoint:

- Uses plain `ws://`, not authenticated `wss://`.
- Has no pairing, device identity, authentication or authorization beyond one-controller-per-session.
- Binds to `0.0.0.0:8765` while the app Activity is running.
- Must only be used on a controlled, trusted LAN or through an ADB emulator port forward.
- Must not be port-forwarded from a router or exposed to the public internet.

M2.4 is responsible for pairing, authenticated TLS control and a hardened trust boundary. M2.2 must not be described as production-secure or fully conformant to the UCP transport-security section.

The existing media URL validator checks HTTP(S), host presence and absence of embedded credentials. It does not yet provide full SSRF, DNS rebinding or redirect protection. Treat M1.5 bearer URLs as credentials.

## Emulator live test

1. Build and install the Android receiver.
2. Launch the app and confirm the UI reports the UCP server listening on port 8765.
3. Run `adb reverse tcp:8765 tcp:8765` from the host.
4. Start `tools/media-host` and retain its temporary MP4 URL privately.
5. From the repository root run:

   ```powershell
   node tools/receiver-simulator/tests/android-receiver-live.mjs --media-url "http://<PC-LAN-IP>:8766/media/<temporary-token>/<file-id>"
   ```

6. Confirm the script passes handshake, session, media load, play, pause, resume, seek, stop and state-event checks.

For a physical TV on the same trusted LAN, connect to `ws://<TV-LAN-IP>:8765/ucp` without `adb reverse`.

## Known limitations

- One active session/player per receiver.
- In-memory session state only; process restart loses session metadata.
- No mDNS advertisement yet (M2.3).
- No pairing or authenticated transport yet (M2.4).
- No volume or track-selection actions.
- `playback.setRate` is not exposed by this endpoint yet.
- No complete redirect/SSRF protection for media origins.
- Media playback uses HTTP(S) fetches; media bytes are never sent over WebSocket.
