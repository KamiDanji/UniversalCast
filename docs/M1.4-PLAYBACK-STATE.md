# M1.4 — Playback State Management

M1.4 extends the Windows receiver simulator with receiver-authoritative playback state transitions and `state.changed` events.

## Implemented request actions

All playback requests require a non-null `sessionId` and an active controller lease.

| Request action | Successful response action | Behaviour |
|---|---|---|
| `media.load` | `media.loaded` | Validates the media descriptor and creates a ready snapshot |
| `playback.play` | `playback.playing` | `ready`, `paused`, or `buffering` → `playing` |
| `playback.pause` | `playback.paused` | `ready`, `playing`, or `buffering` → `paused` |
| `playback.seek` | `playback.seeked` | Sets a non-negative integer position within known duration |
| `playback.stop` | `playback.stopped` | Clears media and returns to `idle` |

Successful response payloads contain `status: "accepted"`, the authoritative `snapshot`, and a `changed` boolean. A repeated `play` while already playing and `stop` while idle are accepted as no-ops (`changed: false`) and do not increment the revision.

The receiver increments `snapshot.revision` exactly once for every externally visible state change. It emits a `state.changed` event containing the new snapshot to connected protocol connections currently attached as controller for that session. Events have their own monotonically increasing outgoing sequence number and are sent after the correlated response.

## Simulator-specific media behaviour

The simulator does not download, decode, or play media. `media.load` validates a media descriptor and transitions directly to `ready` so the control/state protocol can be tested without a media engine. A real receiver must transition through `loading` and only report `ready` after its platform media engine confirms readiness.

Accepted source URIs must be absolute HTTP(S) URLs without embedded credentials. This is only basic syntax validation in the simulator. It does not fetch URLs and is **not** a complete SSRF, DNS-rebinding, redirect, or private-network protection policy. Production receivers must implement the full security requirements in `specifications/ucp/SECURITY.md` and the media URL requirements in `specifications/ucp/UCP-1.0.md`.

The simulator advertises no playable media formats because it has no playback engine. The playback controls are state-machine simulations, not actual media playback.

## Validation rules

- Playback commands are rejected if the connection does not own the session controller lease.
- `play` requires `ready`, `paused`, or `buffering`.
- `pause` requires `ready`, `playing`, or `buffering`.
- `seek` requires a loaded state and a non-negative integer position. If duration is known, the position cannot exceed it.
- `stop` clears the active media descriptor and resets position, duration, buffer and playback rate.
- Invalid transitions and positions return structured `INVALID_MESSAGE` errors with `details.reason` set to `INVALID_STATE` or `INVALID_POSITION`.
- Media URI validation errors use `INVALID_MEDIA_URI`.

## Tests

From the repository root:

```powershell
pnpm --filter @universalcast/receiver-simulator test
pnpm --filter @universalcast/receiver-simulator typecheck
```

For a live two-sender test, keep the receiver running in Terminal 1:

```powershell
pnpm --filter @universalcast/receiver-simulator dev
```

Then in Terminal 2:

```powershell
pnpm --filter @universalcast/receiver-simulator exec node tests/playback-live.mjs
```

The live test verifies media load, play, pause, seek, invalid seek rejection, stop, state events, authoritative snapshots, and controller handover.

## Limitations

- Sessions and playback snapshots remain in memory and are lost when the simulator process exits.
- No actual media engine is connected.
- No pairing, authentication, TLS, or production authorization exists.
- No playback clock advances `positionMs`; seeking updates the stored position only.
- Buffering, ended, error, rate, volume, tracks, and queue operations are not implemented in this milestone.
