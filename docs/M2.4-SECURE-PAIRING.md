# M2.4 — Secure Pairing and Authenticated Control

Status: Android pairing and authenticated WSS implementation added to the debug receiver; cross-platform device validation and production enablement remain pending.

## Goal

Replace the M2.2/M2.3 development-only `ws://` endpoint with a production-oriented `wss://` control channel. A receiver must only process UCP application requests from a sender whose identity has been explicitly paired and whose proof of possession is valid for the current connection.

This milestone is intentionally split into independently testable stages. Do not mark M2.4 complete until the full acceptance criteria at the end pass.

## Security decisions

### 1. Transport encryption and receiver identity

- Use WebSocket over TLS (`wss://`) for every production control connection.
- Require TLS 1.2 or newer; prefer TLS 1.3 when supported by both endpoints.
- The receiver owns a persistent P-256 ECDSA identity key generated and retained by Android Keystore. The private key must never be exported.
- A self-signed receiver certificate is generated from that identity and used by the TLS server. The certificate SHA-256 fingerprint is stable for the lifetime of the receiver identity.
- Senders pin the exact SHA-256 certificate fingerprint obtained through the receiver's local pairing QR flow. Do not accept arbitrary self-signed certificates, hostname-only checks, or trust-on-first-use without user-visible verification.
- No automatic plaintext fallback is permitted. The existing `ws://` development endpoint must be removed or isolated behind an explicitly debug-only build variant before production pairing is enabled.

### 2. Pairing bootstrap

Pairing is receiver-initiated and requires a physical action on the TV:

1. The user selects **Pair a device** on the receiver.
2. The receiver opens a 120-second pairing window and generates a cryptographically random 256-bit, single-use challenge.
3. The receiver displays a QR payload containing only public/bootstrap data: protocol version, receiver ID, secure endpoint, `/ucp` path, TLS certificate fingerprint, challenge, and expiry timestamp.
4. The sender generates its own persistent P-256 signing identity and sends its public key, sender ID/name, and a signature proving possession of the corresponding private key.
5. The receiver verifies the challenge, expiry, signature, and receiver binding. It then presents the sender name and a short authentication string (SAS) for explicit approval on the TV.
6. The user approves or rejects. Approval stores the sender's public identity and role; rejection stores nothing. The challenge is consumed on either decision and cannot be replayed.

The QR code contains no private key, long-lived credential, session token, or reusable bearer secret. Possession of the QR payload alone must not authorize control.

### 3. Authentication on every connection

- After TLS is established and the server certificate has been pinned, the receiver issues a fresh 256-bit connection nonce.
- The sender proves possession of its paired private key by signing a canonical transcript containing the nonce, receiver ID, sender ID, and negotiated UCP version.
- The receiver verifies the signature against the paired sender public key before sending `connection.welcome` or accepting any application request.
- The nonce is single-use, expires after 30 seconds, and is bound to that TLS connection.
- Existing envelope sequence numbers and request-ID deduplication remain required. Authentication does not replace replay protection.
- Unknown or revoked senders receive `NOT_PAIRED` / `NOT_AUTHORIZED`; they cannot create sessions, query private state, or issue playback commands.

### 4. Roles and revocation

- `controller`: may create/join a session and issue state-changing commands, subject to the existing single-controller session rule.
- `observer`: may read permitted receiver/session state but cannot issue state-changing commands.
- A newly paired sender is assigned an explicit role by the receiver; the implementation must not silently elevate an observer.
- The receiver maintains a paired-device list with sender ID, display name, public key, role, and pairing timestamp.
- Revocation deletes the trust record and closes any active connection for that sender immediately.
- Pairing records and receiver identity survive app restarts. A factory reset/recovery flow must be documented before production release.

### 5. Discovery metadata

DNS-SD remains discovery only; it is never proof of identity. The secure advertisement will use `tls=1` and publish the receiver certificate fingerprint in a bounded TXT attribute (proposed key `fp`). It must not publish pairing challenges, sender identities, credentials, or media URLs. The service port remains 8765 unless implementation testing identifies a platform conflict.

## Canonical authentication and pairing transcripts

Both transcripts are byte concatenations with no lengths or separators because every field after the domain is fixed width. UUIDs use their 16 network-order bytes. Nonces and challenges are 32 raw bytes encoded in unpadded base64url in JSON. Public-key fingerprints are SHA-256 of the sender's DER SubjectPublicKeyInfo bytes, not a PEM string.

The pairing transcript is, in order:

1. ASCII `UCP-PAIR-1` (10 bytes)
2. Receiver UUID (16 bytes)
3. Sender UUID (16 bytes)
4. SHA-256 sender public-key fingerprint (32 bytes)
5. Pairing challenge (32 bytes)
6. Sender nonce (32 bytes)

The sender signs the complete 138-byte transcript with ECDSA P-256 and SHA-256. The signature is ASN.1 DER encoded and base64url encoded in the pairing request. The short authentication string is the first four bytes of SHA-256(transcript), interpreted as an unsigned big-endian integer modulo 1,000,000 and rendered as six decimal digits.

The connection authentication transcript is, in order:

1. ASCII `UCP-AUTH-1` (10 bytes)
2. Receiver UUID (16 bytes)
3. Sender UUID (16 bytes)
4. Negotiated UCP major and minor version bytes (for UCP 1.0: `01 00`)
5. Fresh connection nonce (32 bytes)

The sender signs the complete 76-byte transcript with ECDSA P-256 and SHA-256. JSON ordering, whitespace, locale, and timestamps are not signed. A connection nonce expires after 30 seconds, is consumed by its first proof attempt, and is scoped to one TLS connection.

## Implementation stages

### M2.4.0 — Architecture and protocol contract

- [x] Freeze the pairing and authentication transcript encodings, identity formats, expiry, role and revocation behavior.
- [x] Add shared fixed byte-level vectors consumed by Kotlin and Node.
- No production secure-control claim is made while device and sender interoperability remain unverified.

### M2.4.1 — Receiver identity and TLS

- [x] Generate/store receiver identity in Android Keystore (M2.4.1a).
- [x] Derive a TLS 1.2 server context from the Keystore identity and add a debug-only WSS listener on port 8766 (M2.4.1b).
- [x] Add Node certificate pinning before the WebSocket HTTP upgrade.
- [ ] Verify correct and incorrect fingerprint cases on an Android TV/emulator.
- [ ] Move production discovery to authenticated WSS after pairing has been validated; discovery and listeners remain debug-only.

### M2.4.2 — Pairing window and sender trust store

- [x] Add receiver UI for a 120-second pairing window and QR bootstrap data.
- [x] Verify sender P-256 proof of possession and show the sender name/SAS for explicit TV approval.
- [x] Persist sender public keys and explicitly selected controller/observer roles; support rejection and revocation.
- [ ] Validate the full QR and approval flow from a sender on an Android TV/emulator.

### M2.4.3 — Authenticated UCP sessions

- [x] Issue per-connection 256-bit challenges and verify paired sender signatures before `connection.welcome` or control actions.
- [x] Gate unauthenticated WSS requests and restrict observers to ping and snapshots.
- [x] Revoke paired senders and close their active authenticated sockets.
- [x] Add a Node end-to-end pairing/reconnect/authentication utility.
- [ ] Run paired, unpaired, revoked, replayed, expired and wrong-key cases against an Android TV/emulator.

## Acceptance criteria

M2.4 is complete only when all of the following pass:

1. Android unit tests and release/debug builds pass.
2. A Windows/Node client reads the QR bootstrap data and pins its TLS certificate fingerprint before the WebSocket upgrade.
3. A client with an incorrect fingerprint cannot send UCP application data.
4. Pairing requires an open receiver pairing window and explicit approval on the TV.
5. Expired and already-consumed pairing challenges are rejected.
6. A sender without the paired private key cannot authenticate, even if it knows the sender ID and public metadata.
7. A valid paired sender authenticates after reconnect and can perform only its assigned role's actions.
8. Revocation terminates active access and prevents future authentication.
9. Replayed connection signatures/nonces are rejected.
10. No production plaintext `ws://` control endpoint or automatic insecure fallback remains.

## Explicit non-goals

- No custom encryption algorithm or custom key exchange.
- No cloud account, central authentication server, or mandatory internet access.
- No assumption that mDNS or LAN membership is trusted.
- No claim that HTTP media delivery is encrypted by this control-channel milestone; media transport hardening remains a separate requirement.
