
# UniversalCast Protocol (UCP) 1.0 — Draft

Status: Initial project draft  
Transport: WebSocket over authenticated TLS  
Encoding: UTF-8 JSON  
Media transport: HTTP(S)  
Discovery: DNS-SD/mDNS  
Authority: Receiver is authoritative for playback state

## 1. Scope

UCP defines discovery metadata, control messages, pairing/session concepts, capability negotiation, and playback state exchange between a sender and a receiver.

UCP does not define:
- A video codec or guarantee that a codec is supported.
- A DRM system or circumvention mechanism.
- A cloud account or mandatory backend.
- A universal method to install applications on TVs.
- A guarantee that every TV supports every media feature.

## 2. Terminology

- **Sender:** device/application that controls playback.
- **Receiver:** device/application that renders media.
- **Session:** receiver-managed playback context.
- **Controller:** paired sender currently authorized to issue playback commands.
- **Observer:** paired sender allowed to view state but not issue state-changing commands.
- **Media descriptor:** metadata and one or more source references describing content.
- **Capability:** a feature the receiver explicitly advertises.

## 3. Versioning

The protocol identifier is `UCP`. The initial version is `1.0`.

A connection handshake MUST negotiate a mutually supported version before application commands are sent. A sender MUST NOT assume that a receiver supports a feature solely because it supports UCP 1.0; it must inspect the receiver capability set.

Unknown optional fields MUST be ignored. Unknown message types or unsupported actions MUST produce a structured error where the peer can safely respond.

## 4. Transport

The initial control transport is WebSocket over TLS. Plain unauthenticated WebSocket is not acceptable for production control.

Media bytes MUST NOT be carried in UCP WebSocket messages. The receiver fetches media over HTTP(S), including from a sender-hosted local HTTP endpoint where applicable.

## 5. Message envelope

Every application message uses this envelope:

```json
{
  "protocol": "UCP",
  "version": "1.0",
  "type": "command",
  "id": "unique-message-id",
  "sessionId": "session-id-or-null",
  "seq": 12,
  "sentAt": "2026-11-08T20:00:00Z",
  "action": "playback.pause",
  "payload": {}
}
```

Fields:
- `protocol`: MUST equal `UCP`.
- `version`: negotiated protocol version.
- `type`: `request`, `response`, `event`, or `error`.
- `id`: unique message identifier generated by sender.
- `sessionId`: session identifier, or `null` for connection-level messages.
- `seq`: sender-local monotonically increasing sequence number for requests/events; not a global clock.
- `sentAt`: RFC 3339 timestamp for diagnostics; not used as an authority for ordering.
- `action`: namespaced action.
- `payload`: action-specific object.

A response includes `replyTo` referencing the request ID. A receiver MUST NOT execute the same state-changing request ID more than once within its deduplication window.

## 6. Request/response behavior

State-changing requests should receive a response indicating accepted/rejected, not merely an assumption that playback succeeded.

Example response:

```json
{
  "protocol": "UCP",
  "version": "1.0",
  "type": "response",
  "id": "response-001",
  "replyTo": "request-001",
  "sessionId": "session-001",
  "seq": 20,
  "sentAt": "2026-11-08T20:00:01Z",
  "action": "command.result",
  "payload": {
    "status": "accepted"
  }
}
```

`accepted` means the receiver accepted the command for processing. It does not necessarily mean the media engine has completed the operation. The resulting state change is reported separately.

- `connection.hello`

- `session.join`
- `session.leave`
- `session.snapshot`

Media:
- `media.load`
- `media.unload`

Playback:
- `playback.play`
- `playback.pause`
- `playback.seek`
- `playback.stop`
- `playback.setRate`

Volume:
- `volume.set`
- `volume.mute`

Tracks:
- `tracks.list`
- `tracks.selectAudio`
- `tracks.selectSubtitle`
- `tracks.disableSubtitle`

State:
- `state.snapshot`
- `state.changed`

Errors:
- `error`

## 8. Media descriptor

A media descriptor may include:
- `mediaId`: application-defined identifier.
- `title`: human-readable title.
- `sources`: ordered source candidates.
- `mimeType`: declared MIME type.
- `metadata`: optional descriptive metadata.
- `subtitleTracks`: optional external subtitle descriptors.
- `startPositionMs`: optional initial position.
- `headers`: not supported in baseline UCP 1.0; use a scoped media URL or another explicitly negotiated mechanism instead.

Each source contains:
- `uri`: absolute HTTP(S) URI.
- `mimeType`: media MIME type.
- `protocol`: optional value such as `hls`, `dash`, or `progressive`.
- `priority`: optional source preference.

Receivers MUST validate media URLs and MUST NOT blindly follow redirects to arbitrary local or sensitive network destinations.

## 9. Capability negotiation

Receiver capabilities are advertised in `connection.welcome` or a capability response. Examples:
- `media.formats`
- `media.hls`
- `media.dash`
- `playback.seek`
- `playback.rate`
- `tracks.audio.select`
- `tracks.subtitle.external`
- `volume.set`

A sender MUST only expose optional functionality supported by the receiver. Capabilities may include limits and supported MIME types.

## 10. Playback state

The receiver owns the authoritative state and increments `revision` whenever the externally visible session state changes.

A state snapshot includes:
- `revision`
- `status`
- `media`
- `positionMs`
- `durationMs` or `null`
- `bufferedMs` or `null`
- `playbackRate`
- `volume` and `muted` when supported
- selected audio/subtitle track identifiers when supported
- `updatedAt`

The sender reconciles local UI from snapshots and state events. It must not assume that sending a command guarantees the requested state.

## 11. Disconnect behavior

A sender disconnect MUST NOT automatically stop playback.

A reconnecting sender authenticates, joins the existing session if authorized, and requests a fresh snapshot. The receiver may expire sessions according to its own documented policy.

## 12. Error model

Errors contain:
- `code`: stable machine-readable identifier.
- `message`: human-readable diagnostic.
- `retryable`: boolean.
- `details`: optional safe diagnostic object.

Initial codes:
- `UNSUPPORTED_VERSION`
- `UNSUPPORTED_ACTION`
- `INVALID_MESSAGE`
- `NOT_PAIRED`
- `NOT_AUTHORIZED`
- `SESSION_NOT_FOUND`
- `MEDIA_UNAVAILABLE`
- `UNSUPPORTED_MEDIA`
- `INVALID_MEDIA_URI`
- `COMMAND_EXPIRED`
- `INTERNAL_ERROR`

## 13. Conformance

A conforming implementation must:
1. Validate protocol and version fields.
2. Authenticate the control connection.
3. Negotiate capabilities.
4. Reject unauthorized commands.
5. Implement receiver-authoritative snapshots.
6. Avoid sending media bytes through WebSocket.
7. Preserve playback after sender disconnect unless policy says otherwise.
8. Pass the shared conformance fixtures for all implemented actions.

This draft must be reviewed and revised before declaring a stable 1.0 release.
