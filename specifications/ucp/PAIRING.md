# UCP Pairing

Status: M2.4 architecture baseline; implementation pending.

## Goals

- Explicit receiver-side user approval.
- No cloud account required.
- Persistent receiver and sender identities.
- Revocation of paired senders.
- No permanent secret embedded in a QR code.
- Authenticated, encrypted control connections.

## Identity and transport

- Production control transport is WebSocket over TLS (`wss://`), TLS 1.2 or newer.
- The receiver uses a persistent P-256 ECDSA identity key held by Android Keystore. Its self-signed TLS certificate is pinned by SHA-256 fingerprint during pairing.
- The sender uses a persistent P-256 ECDSA signing identity. The private key remains in platform secure storage where available.
- Discovery TXT data may publish the receiver's certificate fingerprint as a hint, but discovery metadata is not trusted until it is matched against the receiver's QR bootstrap data.
- Production clients must not silently fall back to plaintext `ws://` or accept an unpinned self-signed certificate.

## Initial pairing flow

1. The receiver user opens a 120-second pairing window.
2. The receiver generates a 256-bit random, single-use challenge.
3. The receiver displays a QR payload containing receiver ID, secure endpoint, protocol version, certificate SHA-256 fingerprint, challenge, and expiry.
4. The sender creates or loads its persistent signing identity and submits its public key, sender ID/name, sender nonce, and a signature over the pairing transcript.
5. The receiver validates the challenge, expiry, receiver binding, and sender proof of possession.
6. The receiver shows the sender identity and short authentication string to the user.
7. The receiver user approves or rejects. Approval stores the sender public identity and explicitly assigned role. Either decision consumes the challenge.

The QR code never contains a private key, long-lived credential, session token, or reusable bearer secret. A QR challenge by itself does not grant control.

## Authentication on each connection

1. Establish TLS and validate the receiver certificate against the pinned SHA-256 fingerprint.
2. The receiver sends a fresh 32-byte random connection nonce.
3. The sender signs the canonical connection transcript with its paired P-256 private key.
4. The receiver verifies the signature against the stored public key and consumes the nonce.
5. Only after successful authentication does the receiver send `connection.welcome` and accept application actions.

Connection nonces are single-use, expire after 30 seconds, and are bound to one TLS connection. UCP sequence numbers and request-ID deduplication remain mandatory.

## Roles

- `controller`: may create/join a session and issue state-changing commands, subject to session controller exclusivity.
- `observer`: may read permitted state but cannot issue state-changing commands.

The receiver must explicitly assign a role when approving a sender. Revocation removes the trust record and closes any active connection for that sender.

## Signature transcripts

Sign deterministic binary transcripts, not serialized JSON. Use domain separation and fixed field ordering:

- Connection transcript domain: `UCP-AUTH-1`.
- Pairing transcript domain: `UCP-PAIR-1`.
- Fields include receiver ID, sender ID, protocol version, and the relevant 32-byte nonce/challenge. The pairing transcript additionally binds the sender public-key fingerprint.

ECDSA P-256 with SHA-256 is the initial signature algorithm. Cross-platform fixed test vectors are required before implementation is considered interoperable.

## Security requirements

- Pairing challenges are generated by a cryptographically secure random generator, short-lived, and single-use.
- The receiver certificate fingerprint is verified before application data is sent.
- Sender private keys never leave secure storage.
- Discovery metadata is never treated as proof of identity.
- Control connections use authenticated encryption.
- Every connection proves sender possession of a paired private key.
- Pairing and control are protected against replay.
- Device credentials are revocable; revocation closes active access.
- Receiver authorizes each command according to controller/observer role.
- Secrets and tokens must not be written to logs.
